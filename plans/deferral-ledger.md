# Deferral Ledger

Live log of scope cuts during the agent-wire-docling build. Every entry names the **functional impact** in plain English (not just the technical change). Reviewed at every wave gate per `feedback_no_deferral_creep`.

Format:
```
- [status] [phase] Title — Functional impact. Follow-up plan.
```

Status: `proposed` | `accepted` | `rejected` | `resolved` (later lifted)

## Seeded at P3 (pre-flight)

- [accepted] [P1] **Scanned-PDF pipeline not timed in pre-flight.** — Overnight run estimate (3.75h–15h) assumes mixed corpus; if the legal corpus is 95% heavy scans with tables, actual time could exceed 15h. Follow-up: taste-test surfaces timing per stratum; if a scanned stratum shows >5s/page, re-plan the batch.
- [accepted] [P1] **VLM pipeline (granite_docling) not validated end-to-end.** — User can select VLM in Advanced, but quality/speed on Apple Silicon not measured here. Follow-up: taste-test is the empirical check.
- [accepted] [P1] **DOCX/XLSX/PPTX/HTML/LaTeX structural probes not run** (only PDF was probed). — Assumes DoclingDocument surface (prov, self_ref, bbox) is format-agnostic based on Docling's claims. Follow-up: Wave 1 Agent A's fixture set includes one of each; if any format is missing provenance, page-sync fallback applies for that format.
- [accepted] [P3] **poppler-utils not bundled.** — If user runs without `brew install poppler`, `/scan` can't probe PDF text layers and stratification falls back to extension-only grouping (all PDFs go to one bucket). `scripts/start.sh` refuses to launch until installed. `/health` reports it.
- [accepted] [P3] **No HuggingFace token in default setup.** — First-run model download is rate-limited and slower. Follow-up: `scripts/warmup.py` reads optional `HF_TOKEN` env var; document in README once it matters.
- [accepted] [Wave 2] **Bidirectional highlight = element-level via sidecar anchors.** — P1 confirmed the Strategy D anchor mapping is clean. No degradation to page-only needed. (This is the **reversal** of the pre-audit C1 deferral — resolved in pre-flight.)
- [proposed] [Wave 2] **PPTX full-fidelity render may degrade to slide-image-only.** — If `pptx-preview` can't render text on slides reliably, Agent F falls back to server-side rasterized slide images. Impact: reviewer sees the slide but can't click individual text elements.
- [accepted] [Wave 2] **LaTeX render is source-only.** — Reviewer compares raw LaTeX source to converted markdown, no KaTeX render. Impact: equations in LaTeX source are unrendered on the left pane; user has to mentally compile. Acceptable for prototype.
- [accepted] [Wave 2] **Native folder picker not implemented.** — User pastes an absolute path into a text field, clicks Validate. Impact: mild friction. Follow-up: add browser folder picker via `webkitdirectory` in Wave 3 if time permits.
- [accepted] [Wave 2] **Multi-config side-by-side comparison not in prototype.** — Reviewer picks one pipeline per stratum and iterates; no A/B view of OCR vs VLM on the same doc. Impact: iteration takes one extra "re-run" per config variant tried.
- [accepted] [Wave 2] **Pipeline presets not persisted across folders.** — Each new corpus starts from defaults; the taste test learns anew each time. Impact: a user with 5 similar legal cases re-tunes 5 times.
- [accepted] [Wave 2] **Pre-fetch of next sample not implemented.** — Reviewer waits up to a second when moving to next sample. Impact: minor UX friction.
- [accepted] [Wave 2] **No visual-regression testing (Storybook/Chromatic).** — Renderer changes aren't caught automatically. Impact: UI drift possible; caught by wanderer + manual eyeballing only.
- [accepted] [Wave 2] **Observability = NDJSON logs only, no metrics dashboard.** — Per-doc progress and errors written to `data/logs/batch-<id>.ndjson`. Impact: debugging an overnight 1500-doc run means `jq` on logs, no at-a-glance dashboard. Acceptable.
- [accepted] [Wave 3] **CLI wrapper (`scripts/run-batch.sh`) is nice-to-have, not blocking.** — HTTP surface is complete and agent-drivable via `curl`; scripted CLI is polish. Impact: agents driving this prototype need to call endpoints directly vs a convenience wrapper.
- [accepted] [Wave 3] **Docling upgrade not auto-detected on outputs.** — If Docling ships 2.91 later, existing outputs don't know they could re-convert better. Impact: user must manually trigger re-runs. `meta.json` records the version used so it's visible.

## Added during Wave 1

- [accepted] [Wave 1 / Agent A] **Figure image files not extracted to `images/`.** — The per-doc output contract reserves `<hash>/images/<self_ref>.png`, but Agent A keeps Docling's default `ImageRefMode.PLACEHOLDER`. Functional impact: the VizDiff reviewer will see `<!-- image -->` placeholders in markdown instead of rendered thumbnails; the source render on the left pane still shows the figure, so no information is lost for the taste test itself. Follow-up: flip to `ImageRefMode.REFERENCED` in a Wave 2a fix-pass once we confirm Docling emits stable per-ref filenames on DOCX/PPTX too.
- [accepted] [Wave 1 / Agent A] **Per-page OCR confidence not populated.** — `meta.json.quality_signals.ocr_confidence_per_page` is emitted as an empty array. The field is reserved in the schema and the UI badge path exists, but we don't yet read confidence out of Docling's `ConversionResult`. Functional impact: the `ocr_low` warning badge will not fire automatically on scanned docs during the taste test; `empty_page` and `figure_missing` warnings do fire, so reviewers still get visible signal. Follow-up: lift in a small Agent A follow-up or let Wave 2 VizDiff author triangulate via visual diff first.
- [accepted] [Wave 1 / Agent A] **VLM pipeline (`vlm.enabled`) not wired to Docling.** — The param is accepted and round-trips through `pipeline_hash`, but the PDF path still uses the standard CV pipeline regardless of the flag. Echoes the pre-flight P1 deferral. Functional impact: selecting VLM in Advanced currently has no effect on output quality; reruns with VLM toggled produce a different `pipeline_hash` directory but the content is identical. Follow-up: swap in `VlmPipeline` via a second `PdfFormatOption` branch once a tough-scan fixture exists.
- [accepted] [Wave 1 / Agent C] **Crashed jobs do not auto-resume on restart.** — On startup, resume_cleanup() sweeps stale `.tmp/` dirs, releases all `doc_leases`, and marks any `running`/`queued` jobs as `failed` with `error="interrupted by restart"`. Functional impact: after a crash mid-batch, docs already converted are preserved (manifest + docs rows), but the job does not auto-continue — the user must POST /batch again with the same scan_id + pipelines. The per-hash lease + docs-table idempotency makes the re-submit a no-op on already-complete docs, so net behavior is "restart picks up where it left off" from the user's perspective, just with a manual trigger. Follow-up: add an auto-resubmit-on-startup helper if the 1500-PDF overnight run ever actually crashes; skipping for now to avoid surprising the user with jobs running unbidden after app restart.
- [accepted] [Wave 1 / Agent C] **Doc-level retry count not surfaced in manifest.** — Failed docs retry up to 3 times then record the final error; the manifest shows `status: error` and the last error string, but not `attempts: 3`. Functional impact: operator debugging a batch failure sees the terminal error but not whether the doc was flaky-but-failed or hard-broken. NDJSON log has every attempt. Follow-up: add `attempts` to manifest entry if the batch log proves too noisy during the overnight run.
- [accepted] [Wave 1 / Agent B] **PDF stratification degrades when poppler-utils is missing.** — Without `pdfinfo`/`pdftotext`, `/scan` can't distinguish native-text from scanned PDFs and can't determine page counts. All PDFs collapse into a single `pdf` stratum (or `pdf-unknown-{bin}` if page counts become available via another path later). Response includes `poppler_missing: true` so the frontend can surface an install hint. User impact: on a machine without poppler, the taste-test loses per-stratum fidelity for PDFs — reviewer must eyeball native vs scanned themselves and iterate once per whole-PDF bucket. Follow-up: `scripts/start.sh` should block launch until `brew install poppler` (already seeded in pre-flight deferral ledger).

## Added during Wave 2

- [accepted] [Wave 2a / Agent E] **Quality badge overlay renders no warnings on the attention.pdf fixture.** — Backend Agent A's conversion currently emits an empty `quality_signals.warnings` array for native-text PDFs (inherits from the three Wave-1 deferrals: OCR conf unwired, figure placeholder mode, VLM flag not wired). VizDiff's `QualityBadgeOverlay` is correct and will light up the moment the backend emits warnings; nothing to fix on the frontend. Fixture data demonstrates 3 badges on the fixture fallback path (`/dev/vizdiff` with no backend). Follow-up resolves automatically when Wave-1 deferrals lift.
- [accepted] [Wave 2a / Agent E] **Synced scroll uses viewport polling (250ms), not a push channel from the renderer.** — pdf.js has no built-in "visible page changed" event, so `VizDiff` polls `sourceRenderer.getCurrentViewport()` every 250ms and debounces MD-side scroll to ~80ms. Functional impact: a very fast scroll flick can land on page N with the MD still showing N-1 for up to ~330ms before catching up. Acceptable for reviewing. Follow-up: if it feels laggy during the 1500-PDF run, lift polling to 100ms or push from the renderer via an `onViewportChange` callback on `SourceRenderer` (would require a contract edit).
- [accepted] [Wave 2a / Agent E] **pdf.js worker ships as a copied static asset (`public/pdfjs/pdf.worker.min.mjs`), not bundler-imported.** — The contract note suggests importing from `pdfjs-dist/build/pdf.worker.mjs`; Next 15 + Turbopack makes this brittle across dev/prod modes. Current approach copies the worker into `public/` at setup time. Functional impact: if `pdfjs-dist` upgrades, the copy is stale until re-copied. Follow-up: add a `pnpm postinstall` step that rsyncs the worker on each install.
- [accepted] [Wave 2a / Agent F] **PPTX degraded to slide-summary (text-only), not slide-image.** — `pptx-preview` was not already installed and the dep pool was effectively frozen mid-wave; rather than add a speculative dep, Agent F ships a slide-summary renderer built from the DoclingDocument texts (header + bullet list per slide, one card per page). Functional impact: reviewers see per-slide title and body text and can page between slides, but do not see actual slide visuals (fonts, shapes, images, layout). The taste test can still catch textual conversion errors (missing text, bad slide order) but not visual-fidelity issues. Follow-up: if the 1500-doc corpus includes PPTX decks where visual fidelity matters, wire server-side slide rasterization via LibreOffice or python-pptx → PIL in Agent A and fetch rasterized frames here.
- [accepted] [Wave 2a / Agent F] **HTML bidirectional highlight disabled.** — HTML renders in a sandboxed no-scripts iframe (CSP `script-src 'none'`, `sandbox="allow-same-origin"`); `scrollToBbox` is a no-op and `onElementClick` is disabled (origin isolation + Docling HTML coords unreliable). Functional impact: the reviewer can read the HTML source in a safe preview but clicking in the source pane won't jump the markdown pane and vice versa. Source navigation is page-reset only. Acceptable for prototype given HTML is a minority format.
- [accepted] [Wave 2a / Agent F] **DOCX bbox scroll is text-prefix only.** — Docling's DOCX output does not carry reliable pixel bboxes, so `scrollToBbox` is a no-op and element-level scroll goes through a `scrollToSelfRef` helper that looks up the element's expected text and does a prefix walk of the rendered DOM. Functional impact: element highlight in DOCX works when the rendered text matches Docling's stored text within 40 chars (nearly always for headings/paragraphs, less reliable inside tables or heavily-styled runs). When the walker misses, the pane simply doesn't scroll — no false match.
- [accepted] [Wave 2a / Agent F] **XLSX `scrollToBbox` interprets bbox.l/bbox.t as column/row indices, not pixels.** — Backend anchors for XLSX emit grid positions in the bbox slot (since cells have no pixel coords in the Docling surface). This is a convention rather than a contract — if Agent A starts emitting pixel bboxes for XLSX, this renderer will silently miss. Functional impact: today, clicking a cell fires a self_ref event that matches on (page, row, col); if the convention changes the grid navigation breaks quietly. Follow-up: either formalize in `contracts/docling-types.ts` or switch XLSX to a dedicated `grid: {row, col}` field if/when Docling surfaces one.
- [accepted] [Wave 2a / Agent F] **Text/MD/LaTeX renderer uses a regex-based highlighter, not a full parser.** — Prism grammars for MD/LaTeX are unreliable; the inline highlighter colors heads, code fences, bold, lists, and links (MD) and macros, comments, groups, and math (LaTeX). Functional impact: pathological input (nested fences, LaTeX macros containing `{`) may render with slightly off coloring. Source reading is unaffected — it is still the raw source text.

## Added during Wave 2a audit

- [accepted] [Wave 2a / audit] **No DOCX/XLSX/PPTX/HTML fixtures on disk.** — `data/fixtures/` currently contains only `attention.pdf` and `docling-paper.pdf`, so the Wave 2a audit could not end-to-end verify the DOCX text-prefix click resolution, the XLSX `bbox.l=col / bbox.t=row` convention, or the HTML/PPTX render paths against real Docling output. The renderers themselves compile and mount without errors on `/dev/renderers`, and the unit-level seams (registry dispatch, `SourceRenderer` surface, React-wrapper lifecycle) are exercised. Follow-up: drop one representative fixture per format into `data/fixtures/` and re-run the audit end-to-end; flip XLSX and DOCX deferrals to `resolved` or revise them based on what Docling actually emits.
- [accepted] [Wave 2a / audit] **Docling `iterate_items` does not descend into table cells.** — Backend `_build_anchors` emits one anchor per top-level iterable item; on `attention.pdf` this produces 4 `table` anchors and zero cell-level anchors. The PDF hit-test was updated in this audit to pick the **smallest-area** containing anchor so future cell-level anchors would win over the enclosing table, but with today's converter output, clicking inside a table still resolves to the table as a whole, not a specific cell. Functional impact: reviewers can click "somewhere in Table 2" and jump to the table's markdown, but cannot point-and-land on a specific cell. Follow-up: if cell-level navigation matters, extend `_build_anchors` to descend `TableItem.data.grid` and emit per-cell anchors; the renderer is already ready.

## Added during Wave 2b

- [accepted] [Wave 2b / Agent G] **Sample pool is UI-local, not persisted to the taste session.** — Picked samples live in React state; a page refresh re-hydrates the session (approvals, pipelines, locks) but the in-flight un-reviewed samples disappear. Functional impact: a reload mid-session means re-pressing Sample on each stratum to repopulate the review grid — approvals are not lost, only the current "worklist" is. Follow-up: if the overnight 1500-doc corpus needs multi-session continuity, add a client-side store (localStorage) or extend `TasteSessionPatch` with a `pending_samples` field server-side.
- [accepted] [Wave 2b / Agent G] **Source preview inside VizDiff is PDF-only in the taste test.** — Agent F's non-PDF renderers (DOCX/XLSX/PPTX/HTML/text/LaTeX) own their own DOM and don't implement the duck-typed `mount(host)` that VizDiff's `SourceSlot` drives; for non-PDF formats the reviewer falls back to a no-op `SourceRenderer` and the left pane shows VizDiff's `[source renderer — page N]` placeholder. Markdown, Raw MD, and JSON tabs on the right remain fully functional, so reviewers can still approve/reject on those formats — they just can't visually compare against the source preview inside the taste loop. Follow-up: add a `mount(host)` adapter layer around Agent F's React components (portal + container div) so the registry presents a uniform SourceRenderer surface across all formats.
- [accepted] [Wave 2b / Agent G] **Output-dir selection is a one-shot text input.** — On first entry to the Taste stage, the user confirms an output directory (default: `<folder>/.docling-out`). There's no native folder picker (already deferred pre-flight) and no "change output dir" action once a session is created — they would recreate the session via "Start a fresh session" on a scan-mismatch or 404 path. Functional impact: a user who wants to rehome outputs mid-taste must start over. Acceptable for prototype.
- [accepted] [Wave 2b / Agent G] **Live convert progress is coarse-grained per sample.** — Each sample row shows `converting…` / `ready` / `convert failed`, but there's no per-doc page count / ETA during conversion. For heavy scanned PDFs that take tens of seconds, the reviewer sees a spinner chip with no more detail. Follow-up: reuse BatchRun's per-doc progress surface for in-taste conversion polling if it feels opaque during the overnight run.
- [accepted] [Wave 2b / Agent H] **Pause is a documented no-op.** — The Pause button and the `P` shortcut fire a toast explaining the resume pattern (cancel + re-POST /batch preserves already-completed docs via the `source_sha256 + pipeline_hash` idempotency key), but there's no true "suspend workers, resume later" state. Functional impact: a user who wants to stop-and-continue must cancel, confirm the finished docs, then re-start — slightly jarring UX. Follow-up: either hide the Pause affordance entirely or wire a genuine pause primitive in Agent C's queue (`/batch/{id}/pause` + `/resume`) before the 1500-PDF run if overnight-pausing matters.
- [accepted] [Wave 2b / Agent H] **"Show in Finder" falls back to "Copy path."** — Native Finder reveal requires a Tauri / shell bridge that isn't in the prototype. We offer a "Copy path" button on the completed export instead, which lets the user paste into a Finder "Go To Folder" dialog (Cmd-Shift-G). Functional impact: two extra keystrokes on export; not blocking.
- [accepted] [Wave 2b / Agent H] **Live log tail derives events client-side from job deltas, not from the NDJSON file.** — The LiveProgress "Recent events" surface generates entries like `+N doc(s) completed` / `status → running` by diffing consecutive Job snapshots. It doesn't tail `data/logs/batch-<id>.ndjson` directly. Functional impact: operators don't see per-doc error reasons or individual file paths live — they appear after the fact in the manifest/outliers view. Acceptable for the prototype; the ledger already accepts NDJSON-only observability.
- [accepted] [Wave 2b / Agent H] **Runtime estimates are coarse heuristics, not scan-informed.** — Pre-launch "Estimated runtime" uses bin midpoints (e.g. 25 pages for `pdf-native-11-50`) × per-page-second constants (0.6s native, 2.5s scanned OCR, 4s VLM). It does NOT read actual page counts from `scan.strata` per doc, nor does it use any historical timing. Functional impact: the estimate is a rough band, not a tight prediction; fine for "kick before bed" planning, poor for commit-by commit tuning. Follow-up: once Agent A emits `runtime_ms` in per-doc meta, BatchRun can compute a running average per stratum and tighten the estimate on re-entry.
- [accepted] [Wave 2b / Agent H] **Outlier-review drawer renders a stub source for non-PDF formats.** — Mirroring Agent G's deferral, the drawer constructs a `PdfRenderer` class for PDF docs and a `makeStubRenderer()` for DOCX/XLSX/PPTX/HTML/text/LaTeX — the markdown + JSON tabs remain fully functional but the left pane shows the VizDiff `[source renderer — page N]` placeholder. A banner is shown in the drawer noting this. Follow-up: same as Agent G — add a `mount(host)` adapter around Agent F's React renderers so the class-surface is uniform.
- [accepted] [Wave 2b / Agent H] **Taste-session handoff is URL-param-primary, localStorage-fallback.** — BatchRun reads the active taste session from `?session=...` (Agent G's URL convention), with `?taste_session=...` as an alias and a `docling:taste_session_id` localStorage key as a multi-tab fallback. There's no server-side "active session" record. Functional impact: if the user clears the URL and localStorage simultaneously, BatchRun goes back to the "approve a stratum in Taste first" empty state and they have to re-enter Taste to select a session. Acceptable.

- [resolved] [Wave 3 wanderer] **Batch worker couldn't find conversion function — all docs failed silently.** — `backend.jobs.batch._call_convert` imports `backend.conversion.convert` and looks for `convert_doc(source_path, output_dir, pipeline)`, but Agent A shipped `backend.conversion.converter.convert_source` with no adapter module. Every batch job completed with `docs_failed == docs_total` and the only breadcrumb was in the NDJSON event log (no events table, so also invisible in sqlite). Fix: added `backend/backend/conversion/convert.py` that wraps `convert_source` in `asyncio.to_thread` and returns `outcome.meta`. End-to-end flow now passes.
- [open] [Wave 3 wanderer] **/strata/sample ignores the `stratum` filter.** — POSTing `{"scan_id":..., "stratum":"pdf-native-1-10", "n":2}` returns picks for ALL strata, not the requested one. Callers can filter client-side so this isn't blocking, but the request shape suggests single-stratum intent. Follow-up: either honor `stratum` (filter docs list server-side) or drop the field from the request schema.
- [open] [Wave 3 wanderer] **Batch status string is `completed`, job-dispatch string-set elsewhere uses `done` / `complete`.** — `run_batch` writes `status="completed"` on normal exit; per-doc status writes `status="complete"`; the build-plan narrative says poll until "done". Harmless today (clients just compare against "queued"/"running"), but it's a footgun for anyone grepping or switching on the enum.
